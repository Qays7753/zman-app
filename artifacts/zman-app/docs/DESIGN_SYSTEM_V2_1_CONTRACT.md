# عقد نظام تصميم Zman v2.1

**الحالة:** مرجع تنفيذ مرحلي، مع أقسام مجمدة صراحةً.

**المنصة الأساسية:** هاتف محمول، مع اعتماد Samsung Galaxy S25 كمرجع بصري أولي.

**المقاسات المرجعية:** 360×780 و390×844 CSS px، مع اختبار 320px و430px عند اكتمال كل مكوّن.

**المالك:** يحدد في سجل التغيير لكل مرحلة؛ لا تعديل صامت على هذا العقد.

## 1. الغرض والنطاق

هذا العقد يحدد اللغة البصرية والمكوّنات وقواعد تجربة الهاتف التي يجب أن تظهر في Zman. لا يملك هذا الملف وحده صلاحية تغيير قاعدة البيانات أو Server Actions أو Queries أو دورة الطلبات والمالية. أي قرار يجمع بين الشكل والسلوك يوثق في هذا العقد بصرياً، ويملك قرار السلوك ملف المجال المقابل.

| الطبقة | ما يقرره هذا العقد | مالك القرار عند التأثير السلوكي |
|---|---|---|
| Design system | tokens، الخط، المسافات، الأزرار، البطاقات، الحدود، الحالات المرئية، الحركة، التباين | مالك التصميم |
| Product behavior | حالات الطلب، الأفعال التالية، Action Dock، قواعد العربون، العكس، الرد، أسباب المخزون | مالك المجال المالي/الطلبات |
| Platform | offline، PWA، caching، analytics، الطباعة، dark mode، تحميل الخط | مالك المنصة مع مالك التصميم |

## 2. الحالة التنفيذية والتجميد الانتقائي

| القسم | الحالة | المسموح الآن |
|---|---|---|
| الأسس والتوكنز | معتمد مبدئياً | إنشاء tokens وتجربة المكونات دون تغيير المنطق |
| الألوان والتباين | معتمد مبدئياً | تطبيق الأدوار مع فحص التباين لكل تركيبة |
| الخط والأرقام | معتمد للاختبار | تجربة الخط والأوزان والـsubset قبل التثبيت النهائي |
| RTL | معتمد مبدئياً | إصلاح الخصائص الاتجاهية مع توثيق الاستثناءات |
| المكونات المشتركة | تنفيذ مرحلي | تحديث Button/Card/Badge/Sheet/Toast بعد اللقطات والفحوص |
| Action Dock | **مجمد** | لا تنفيذ قبل استخراج state machine من الكود |
| الرسوم | **مجمد جزئياً** | لا اعتماد لألوان السلاسل قبل اختبار الخلفية والنمط والتسمية والرمادي |
| تكبير الخط والشريط السفلي | **مجمد جزئياً** | لا حذف labels؛ يلزم تصميم reflow واختبار 100/130/200% |
| offline | **مجمد سلوكياً** | توثيق العرض فقط؛ منع/سماح الحفظ قرار منصة ومنطق مالي |
| الطباعة | **نطاق مستقل** | لا يؤخر تحديث الهاتف والمكونات |
| الوضع الداكن | **مخطط لاحقاً** | لا يغير الوضع الفاتح في هذه المرحلة، مع إبقاء semantic roles قابلة للتوسع |

## 3. مبادئ التصميم

1. تُصنع الهرمية بالمكان والحجم والوزن قبل اللون.
2. لكل دور بصري semantic token واحد؛ قد تتشارك الأدوار قيمة خاماً، لكن لا تستخدم القيمة الخام مباشرة في المكونات.
3. لا يحمل اللون معلومة وحده؛ الحالة تحتاج نصاً أو رمزاً أو نمطاً.
4. الأخضر يوجه الإجراء ولا يملأ الشاشة.
5. الفعل ذو الأثر المالي يشرح أثره قبل التنفيذ وبعده.
6. حالة النظام الافتراضية هادئة؛ لا توهج أو تدرج أو حركة بلا سبب.
7. كل رقم تصميمي إما token مقاس أو هدف معلّم بأنه يحتاج قياساً.

## 5. التباين وقابلية الوصول

| النوع | معيار Zman |
|---|---:|
| نص عادي | 4.5:1 أو أعلى |
| نص كبير | 3:1 أو أعلى |
| عنصر غير نصي وظيفي | 3:1 أو أعلى عند الحاجة |
| target داخلي | 48×48 CSS px مفضلة/معتمدة داخلياً |
| عدم الاعتماد على اللون | إلزامي للحالات والأرقام الدلالية |

48px معيار منتج داخلي أكثر تحفظاً من حد WCAG الأساسي، وليس ادعاءً تنظيمياً. كل تركيبة جديدة تفحص مقابل السطح الفعلي، وكل سلسلة رسم تفحص مقابل الخلفية الفعلية، لا مقابل سلسلة أخرى فقط.

## 6. الخط والأرقام

الخط الحالي **Tajawal** يبقى في مرحلة التثبيت الحالية لتجنب تغيير شامل غير مقاس. يُختبر IBM Plex Sans Arabic كتجربة مستقلة قبل اعتماده، لأن الاختيار يحتاج اختبار شخصية العلامة، وضوح العربية، الأرقام، حجم subset، والوزن على Samsung S25.

| القاعدة | القيمة |
|---|---|
| النص الأساسي | 16px على الأقل في الحقول؛ باقي الأحجام عبر semantic scale |
| مناطق النص | `rem` أو tokens متجاوبة، لا قيم عشوائية |
| المبالغ | `tabular-nums` و`lining-nums` بعد التحقق من الخط الفعلي |
| الاتجاه | المبلغ داخل `bdi dir="ltr"` مع label عربي |
| العملة | «د.أ» بعد الرقم بصيغة موحدة |
| القيمة الفارغة | «—»، والصفر الحقيقي `0.000` |
| التاريخ | صيغة عربية موحدة؛ أي استثناء يوثق |

أي ميزانية تحميل خط أو مدة تنفيذ تُكتب كميزانية/هدف يحتاج قياساً، لا كحقيقة عامة.

## 8. المكونات المشتركة

### الأزرار

الزر الأساسي واحد بصرياً في الشاشة. ارتفاع `lg=52px`، و`md=48px`، و`sm=40px` مع منطقة لمس حقيقية 48px داخل صف بطاقة. يجب أن يصف النص الفعل، مثل «حفظ الطلب» و«تأكيد رد العربون»، لا «موافق» أو «تم» كإجراء أساسي.

حالة `disabled` تشرح السبب بنص مساعد أو لا تعرض الزر إن لم يكن قابلاً للتفعيل. لا يعتمد الهاتف على `title`. حالة النجاح ليست إلزامية لكل زر؛ الأفعال المالية تحتاج رسالة نتيجة تحمل الرقم والأثر.

الأفعال المدمرة المالية ترتب عمودياً في الهاتف: الإلغاء أولاً، والفعل المدمّر بعد مسافة واضحة. لا يدمج «عكس التسليم» مع «عكس احتجاز العربون».

### الحقول

البنية: label واضح، حقل 48px، رسالة مساعدة أو خطأ في مكانها. التركيز مرئي، والحد الوظيفي ليس `hairline`. حقول الأرقام تستخدم `inputmode="decimal"` بعد فحص سلوك caret والنسخ واللصق في Chrome Android وSafari.

### البطاقات والحالات

بطاقة الطلب تحافظ على ترتيب قابل للتوقع، لكنها يجب أن تتعامل مع الأسماء والمبالغ والتواريخ الطويلة وعند 200% دون قص. Badge الحالة يستخدم أيقونة من مكتبة Lucide مع نص الحالة؛ رموز Unicode العشوائية ممنوعة.

### Bottom Sheet وToast

الورقة لها تمرير مستقل وsafe-area وحبس تركيز عند الحاجة، وتغلق بزر واضح أو السحب أو النقر على الطبقة وفق نوعها. ارتفاع 85vh سقف وليس هدفاً. أخطاء العمليات تظهر inline أو في رسالة ثابتة قابلة للإغلاق مع Retry؛ لا يترك Toast خطأ دائماً فوق المحتوى.

### الشريط السفلي وFAB

الشريط السفلي يحافظ على النصوص عند تكبير الخط؛ إذا لم تكف المساحة، يعاد تصميم reflow أو ينقل عنصر منخفض الأولوية إلى «المزيد». لا تحذف المعلومة المرئية وتكتفي بـ`aria-label`.

مساحة المحتوى السفلية شرطية: تحجز مساحة للشريط السفلي وFAB أو Action Dock فقط عندما تكون هذه العناصر موجودة فعلياً. الـFAB لا يغطي آخر بطاقة أو حقل، ويختفي عند وجود Action Dock إذا تعارض معه.

## 9. Action Dock — مجمد حتى مطابقة الكود

لا يحتوي هذا العقد على جدول حالات وأفعال مخترع. قبل التنفيذ يجب استخراج مصفوفة من الكود تشمل:

| الحقل المطلوب | المصدر |
|---|---|
| status الحالية | أنواع/ثوابت الحالات ومسار القراءة |
| nextStatuses | transitions والـguards الفعلية |
| الأفعال المتاحة | Server Actions والواجهات الحالية |
| شرط العربون | منطق deposit وintegrity checks |
| شرط الرقم | وجود رقم للاتصال الخارجي |
| شرط سجل الاحتجاز | وجود حركة أو مبيعة احتجاز فعلية |
| قابلية العكس | المسار العكسي المطابق لنوع التسوية |

بعد استخراجها، يكتب جدول Action Dock في وثيقة مجال منفصلة، ويُختبر read-only أولاً. لا تُعاد كتابة Server Actions أو Queries ضمن مرحلة التصميم البصري.

## 10. الرسوم

لا تستخدم أكثر من لونين كخيار Zman افتراضي لتقليل الالتباس، لكن هذا معيار تصميم داخلي لا قاعدة WCAG. كل سلسلة تحتاج تسمية مباشرة، نمطاً مميزاً مثل `stroke-dasharray` أو marker، وجدول قيم أو عرضاً رقمياً.

اللون الفاتح لا يستخدم خطاً منفرداً على White أو سطح تحليلي فاتح إذا فشل تباينه؛ يمكن أن يكون تعبئة مع حد Steel داكن. يجب اختبار الرسم على الخلفية، grayscale، وحالات عمى الألوان.

## 11. الحالات والاتصال والمنصة

حالات empty/loading/error/offline مرئية في التصميم، لكن مالك سلوكها يحدد في كل PR. تصميم الحالة لا يقرر وحده منع الحفظ المالي أو المزامنة أو التخزين المؤقت. هذه البنود تحتاج مراجعة منصة ومنطق مالي قبل التنفيذ.

## 12. الهاتف والتكبير وRTL

يختبر كل مكوّن عند 100% و130% و200%، وعلى 320 و360 و390 و430px. عند التكبير يعاد تدفق المحتوى إلى أسطر أو مجموعات، ولا يحذف النصوص المهمة. الجداول والرسوم قد تملك تمريراً محلياً إذا كانت ذات طبيعة ثنائية الأبعاد، بينما تبقى العناوين والفلاتر وأدوات الصفحة قابلة لإعادة التدفق ضمن العرض.

تستخدم الخصائص المنطقية عندما يكون المقصود اتجاهاً (`margin-inline` و`inset-inline`). أي `left/right` تقني يوثق سببُه. الأسهم الاتجاهية تعكس، بينما رموز الحالة لا تعكس. أسماء المنتجات والأرقام وأرقام الهاتف تحاط بـ`bdi` أو `dir="ltr"` عند الحاجة.

## 13. بوابة إضافة أو تعديل token

لا يضاف لون أو مسافة أو حجم جديد إلا إذا أجاب الـPR كتابةً:

1. ما الدور الذي لا يغطيه token قائم؟
2. على أي سطح يظهر؟
3. ما تباينه مع كل سطح يستخدمه؟
4. ما تباينه مع العناصر المجاورة؟
5. ما المقابل في الوضع الداكن أو لماذا لا ينطبق؟
6. من مالك القرار؟
7. ما لقطة الهاتف التي تثبت الحاجة؟

نقص إجابة جوهرية يعني إرجاع الـPR للمراجعة.

## 14. تعريف الإنجاز

لا يعتبر المكوّن منجزاً قبل أن يملك الحالات المطلوبة، ويثبت التباين، ويملك منطقة لمس 48px، focus-visible، RTL، 320/360/390/430px، تكبير 100/130/200%، reduced motion، وحالة loading/error عند الحاجة، ويخلو من hex مباشر داخل المكونات.

## 15. طريقة الفروع والفحوص

كل مرحلة على فرع مستقل من `main` أو من آخر مرحلة مدموجة. لا تعديلات مباشرة على `main`. الحد الأدنى للفحوص: `pnpm typecheck`، `pnpm build`، `git diff --check`، جرد الألوان، لقطات 360×780 و390×844، وفحوص المجال عند لمس الأفعال أو الانتقالات.

سجل التغيير يسجل: التاريخ، الفرع، القسم، token أو المكوّن، ما تغير بصرياً، ما لم يتغير سلوكياً، نتائج الفحوص، والمالك الذي راجع الاستثناء.
