# Zman Header & Home v2.2 Contract

## نقاط النقاش الرئيسية

هذا العقد يكمّل `DESIGN_SYSTEM_V2_1_CONTRACT.md` ويصحّح تنفيذ الرأس السابق. الهدف هو **توحيد الشريط الموجود**، لا إضافة شريط جديد. يبقى رأس AppShell هو المساحة الوحيدة التي تجمع عنوان الصفحة وأفعالها، بينما يبقى محتوى الصفحة ومساحته كما كان.

## 1. عقد الشريط العلوي الواحد

### 1.1 البنية

| الجزء | القاعدة |
|---|---|
| الرأس | صف واحد فقط داخل AppShell؛ لا يوجد ContextBar أو toolbar رأسي مستقل تحته. |
| العنوان | عنوان واحد واضح، وزن 700 وحجم 16px على الهاتف، ويأخذ المساحة المرنة المتاحة. |
| الإجراء الأساسي | إجراء أساسي واحد مرئي عند وجوده، باستخدام Button المشترك أو مجموعة صغيرة داخله. لا يتكرر في صف آخر. |
| أفعال السياق | أفعال الطلبات والمالية والبحث والتصفية والتبديل تبقى داخل الصف نفسه وبأهداف لمس 48×48px. |
| العدد | يظهر في الصف عدد محدود يمكن فهمه فوراً؛ الأفعال الثانوية الكثيرة تستخدم زر «أدوات الصفحة» الموحد بدلاً من إضافة صف جديد. |
| التبويبات | إذا ظهرت داخل الرأس، تستخدم نمطاً موحداً ومضغوطاً ولا تفرض ارتفاعاً إضافياً. لا تتحول إلى شريط مستقل. |
| التمرير | لا يعتمد الرأس على تمرير أفقي خفي لإظهار فعل أساسي أو عنوان. إذا ضاقت المساحة، تُجمع الأفعال الثانوية في الأدوات. |
| الارتفاع | يبقى ارتفاع AppShell كما هو: 56px للهاتف و64px لسطح المكتب. لا يضاف أي ارتفاع رأسي بسبب التوحيد. |
| RTL | العنوان والأفعال يتبعان الاتجاه المنطقي، وزر الرجوع يستخدم الأيقونة والlabel المناسبين للسياق نفسه. |

### 1.2 دلالة الأنماط

| النمط | الاستخدام المسموح |
|---|---|
| `primary` Forest | الإجراء الأساسي الوحيد مثل طلب جديد أو تسجيل عملية. |
| `default` Paper بحد | أداة سياقية مثل تبديل العرض أو فتح الفلتر أو التحديث. |
| `quiet` شفاف | أداة ثانوية فقط، ولا يستخدم لإخفاء إجراء يومي مهم. |
| `destructive` | الحذف أو الإلغاء النهائي مع فصل بصري وتأكيد مناسب. |
| `tab` | تبويبات داخل مجموعة الرأس نفسها عند الحاجة، بمقاس موحد لا يصنع شريطاً جديداً. |

### 1.3 قواعد توحيد الصفحات

| الصفحة | تركيب الصف الواحد |
|---|---|
| الرئيسية | «لوحة القيادة» + محدد الفترة بنفس Button موحد. تبقى الأولويات داخل المحتوى ولا يضاف لها رأس آخر. |
| الطلبات | «الطلبات» + «طلب جديد» كإجراء أساسي، ثم بحث وتصفية وتبديل العرض وأدوات الصفحة بنفس عائلة الأزرار. |
| تفاصيل الطلب | «تفاصيل الطلب» مع الرجوع في الموضع نفسه؛ Action Dock داخل الطلب وليس في رأس إضافي. |
| المالية | «المالية» + أدوات التبويب والبحث والفلاتر داخل الصف نفسه؛ لا تركيب مختلف بين المدفوعات والمبيعات والحسابات. |
| التقارير | «التقارير» + تحديث عند الحاجة، والتبويبات والفترات داخل المحتوى دون فرض شريط رأسي جديد. |
| المخزون والكتالوج والملاحظات | نفس ارتفاع الرأس وشكل الإضافة والبحث والأدوات، مع اختلاف labels فقط. |

## 2. الصفحة الرئيسية

يمكن تحسين فهم الصفحة الرئيسية داخل مساحة المحتوى الحالية، لكن لا يجوز أن يضيف التحسين صفاً فوق المحتوى. الترتيب المقترح للمحتوى هو: «يحتاج انتباهك» عند وجود حالة فعلية، ثم «ملخصك الآن»، ثم «الوصول السريع»، ثم «التحليل المالي»، ثم التفاصيل القابلة للطي. هذا الترتيب لا يغيّر queries أو البيانات ولا يزيد ارتفاع الرأس.

محدد الفترة يبقى في رأس AppShell الواحد. لا يظهر محدد ثانٍ لنفس الفترة داخل الصفحة. كل عنوان قسم يشرح وظيفته، ولا تعتمد الأولوية على اللون وحده.

## 3. حدود التغيير

التنفيذ المرئي يقتصر على AppShell، مكونات الرأس، تركيب الصفحات، labels وclasses وترتيب المكونات. ممنوع تعديل `queries.ts` أو `actions.ts` أو مخطط قاعدة البيانات أو الحسابات المالية أو روابط Action Dock.

## 4. معايير القبول

| المعيار | معيار النجاح |
|---|---|
| رأس واحد | لا يوجد أكثر من صف علوي ثابت بين عنوان الصفحة والمحتوى. |
| المساحة | ارتفاع الرأس لا يزيد عن baseline السابق، ولا تنخفض مساحة المحتوى بسبب التوحيد. |
| الاتساق | أزرار الطلبات والمالية والكتالوج والملاحظات تستخدم نفس الأحجام والحدود والنصف قطر وحالات focus، مع اختلاف label/icon فقط. |
| الهاتف | عند توفر CSS viewport حقيقي 360px أو 390px لا يوجد قص أو تمرير أفقي مخفي للإجراء الأساسي. |
| السلامة | لا تغيير في DB أو queries أو actions أو mutations. |
